ADaM LangGraph Phase 1-7 完成情况检阅

这份文件只总结新架构项目 D:\Archive\Research\Projects\ADaM_Shiny_LangGraph 在 Phase 1 到 Phase 7 做成了什么、没做成什么，以及哪些能力是真实执行、哪些仍然是 mock/stub。当前失败的 Phase 8 UI 不计入本报告成果。

先给结论

Phase 1-7 的后端架构主线已经搭起来了：系统已经从“旧 Shiny 单节点大提示词”转成了一个可编排的本地后端原型。它能管理 study 文件夹、扫描输入、维护状态、规划 ADaM 数据集依赖、调用 LLM 边界、生成/保存 R 代码、用本地 Rscript 执行、写审计文件，并对失败做初步诊断和一次受控修复。

但这不是一个已经好用的产品：UI 没有成功，ADSL 以外的数据集还不是稳定的临床生产规则生成器，验证也主要是结构性验证，不是 CDISC/P21 级别合规验证。

维度当前真实状态
产品形态后端原型已成型；人用 UI 失败，需要重做。
输入模型支持 study 文件夹结构：input_sdtm、input_spec、reference_adam、legacy_code、input_define、runs。
真实生成能力ADSL 有 deterministic R 路径；下游 ADaM 有 LLM 生成 R 代码并进入 R 沙盒的通路，但临床逻辑仍依赖用户 spec、输入数据和 LLM 输出质量。
LLM 能力已有 OpenAI-compatible、Claude/Anthropic、DeepSeek/Qwen alias、custom base URL 的配置边界；真实调用需要显式允许外部 API 和 API key。
R 执行能力已有本地 Rscript 执行边界，可使用 C:\Dev\R-4.5.2\bin\Rscript.exe。.sas7bdat 主要走 R/haven 读取。
审计能力run 目录下写入 dependency plan、LLM response、generated R、validation、diagnostics、manifest 等文件。
主要风险UI 方向错误；下游数据集业务规则不应被误称为“生产级真实生成”；依赖抽取和验证仍是 MVP 水平。

整体架构到底做成了什么

用小白能理解的话说，Phase 1-7 搭的是“后台工厂”，不是“最终软件界面”。

用户准备 study 文件夹
  -> 系统扫描有哪些 SDTM、spec、参考 ADaM、SAS/define 证据
  -> 系统判断要生成哪些 ADaM，以及它们互相依赖什么
  -> 每个目标数据集进入自己的 DatasetGraph
  -> DatasetGraph 准备 LLM 上下文
  -> LLM 返回严格 JSON，里面包含 R 代码、假设、风险点
  -> 系统保存原始回复、解析结果、R 脚本
  -> Rscript 执行生成的 R 脚本
  -> 系统检查输出文件是否存在、结构是否基本正确
  -> 系统写 validation、diagnostics、audit manifest

这说明后端链条已经存在。现在最大问题不是“完全没架构”，而是 UI 没有按这个工作流让用户理解和控制系统。

Phase 7：多数据集 study 编排

这一阶段解决的是：从“只跑一个 ADSL”升级为“用户请求多个 ADaM 时，系统知道依赖、顺序、可用性、是否需要用户决策”。

7.1 依赖规划

  • 新增 src/adam_agent/graph/dependencies.py。
  • 定义 DatasetDependencyPlan。
  • 把依赖决策记录成：依赖列表、来源、置信度、是否需 review、原因。
  • 非 ADaM 目标如 LB、DM 不会被 stub 成 completed，而是标为 unsupported。
  • downstream-only 请求能识别 foundation dependency，但后来已改成不静默执行缺失依赖。

7.2 spec-first 依赖证据

  • 依赖提取优先看 input_spec。
  • 如果 input_spec 存在，legacy SAS 和 define.xml 只做冲突检查，不改变依赖计划。
  • 如果没有 input_spec，才用 legacy SAS、define.xml 等作为 draft 证据。
  • 没有证据时才使用 MVP fallback。
  • 支持执行批次，例如 ADSL -> ADLB -> ADTTE。
  • 中间数据集失败时，只阻断依赖它的数据集，不污染不相关数据集。

7.3 文件化依赖审查

  • 写入 runs/{run_id}/planning/dependency_plan.json。
  • 写入 runs/{run_id}/planning/dependency_review.md。
  • 写入 study-level runs/{run_id}/audit/manifest.json。
  • 引入 review status：accepted、review_required、warning、blocked。
  • 如果 spec 文件夹存在但覆盖不到某个目标数据集，会记录 coverage-gap warning。

7.4 通用依赖可用性检查与 LLM 下游路径

  • 把“发现依赖”和“执行依赖”拆开。
  • 系统可以自动发现依赖，但不能静默执行缺失依赖。
  • 可用依赖来源包括 reference_adam/{dataset}.csv、reference_adam/{dataset}.sas7bdat、当前 run 输出。
  • CSV 依赖要能读 header 才算 usable。
  • .sas7bdat 依赖在 Python 侧会先标 found_but_unusable，因为这个阶段没有 Python profiling；R 侧读取能力另算。
  • 新增 LLM context package：把目标 spec、SDTM profile、依赖数据 profile、输出路径、暴露策略、warnings 打包给 LLM。
  • 新增 LLM JSON 输出 contract：必须包含 dataset、r_code、assumptions、risk_points、used_inputs、expected_outputs。
  • 新增 generated R 安全预检查，禁止明显危险调用，如 system()、shell()、unlink()、download.file()、install.packages()。
  • 新增 generic downstream runner：context -> LLM -> parse/write R -> R runner -> structural validation。

7.5 LLM provider 边界

  • 新增 OpenAI-compatible client，支持自定义 base URL 和任意 model string，不做过窄模型白名单。
  • 新增 provider factory：LLMProviderConfig 和 build_llm_client()。
  • 支持 provider alias：OpenAI-compatible、DeepSeek、Qwen、Anthropic/Claude。
  • Anthropic 使用 Messages API 形态。
  • 外部 provider 必须显式 external_api_allowed=true 且提供 API key。
  • 真实 provider 不会失败后自动 fallback 到 mock。
  • custom base URL 必须显式允许，并在 audit 中记录 relay 风险。

7.6 provider 模式接入图

  • 新增 execution_mode = llm_downstream_provider。
  • StudyGraph 把 llm_exposure 和 llm_provider 传给 DatasetGraph。
  • DatasetGraph 通过 factory 构造真实/模拟 provider client。
  • CLI 新增 adam-agent run-study，可以用 JSON config 跑 study。
  • provider 配置错误会 fail-closed，记录 provider/model/base URL/risk flags。

7.7 下游真实 R sandbox

  • 新增 execution_mode = llm_downstream_r_sandbox。
  • 该模式会让 LLM 生成 R，然后用本地 Rscript 真实执行。
  • 生成脚本必须位于 runs/{run_id}/code/ 下。
  • 输出必须写到 runs/{run_id}/outputs/{dataset}.csv。
  • validation report 会记录 r_stdout 和 r_stderr。
  • 曾做过一次真实外部 API smoke：OpenAI-compatible relay + gpt-5.5 + 本地 Rscript，ADAE 输出结构验证通过。

7.8 下游失败诊断与一次修复

  • 新增 src/adam_agent/downstream/diagnostics.py。
  • 下游失败会写 runs/{run_id}/diagnostics/{dataset}_failure_report.json。
  • 只有 code contract、R runtime、output contract 这类问题允许触发一次 repair_code。
  • 缺源变量、spec 冲突、依赖缺失、sandbox policy、R 环境配置问题不能靠盲目修代码掩盖。
  • repair prompt 会带上上下文、原始 LLM 回复、R 代码、validation report、stdout/stderr、JSON contract。
  • repair artifact 用 repair1 后缀保存，便于审计。

mock / stub / real 到底怎么区分

词意思在本项目里的例子能不能当真实生成
mock假 LLM 或假外部服务，用固定返回测试流程。MockLLMClient不能。只能证明接口和流程。
stub占位实现，不执行真实核心逻辑。StubRRunner、completed_stub不能。只能证明编排和 artifact。
real_adsl_minimal真实跑本地 R 生成 ADSL starter。DM/EX -> build_adsl.R -> adsl.csv可以说是真执行，但不是完整生产 ADSL。
llm_downstream_provider真实或配置 provider 生成代码，但 R 执行可仍是 stub。provider + structural stub runner不能完整算真实执行。
llm_downstream_r_sandboxLLM 生成 R，系统保存代码，本地 Rscript 真实执行。ADAE smoke 路径能证明生成-执行链路，但不证明临床推导正确。

真实限制和下一步应怎么纠偏

已经确定的限制

  • 当前 UI 把用户暴露给了太多后端 artifact 和 JSON，失败。
  • demo 数据映射曾经搞错：ae/dm/ex 是 SDTM，ads_adae_full/ads_adsl_full 是 spec，adae/adsl 是 reference ADaM，PSY201 是另一个项目。
  • Phase 7 后端不是没有价值，但 UI 没有把“上传/识别/生成/执行/审查/比较”的产品流程表达出来。
  • ADSL 以外的真实临床逻辑不能写死在代码里，应该由用户 spec + LLM + R sandbox + review 支撑。
  • validation 目前是结构验证，不是监管级 ADaM 合规验证。
  • 依赖 fallback 是 MVP 排序保护，不是完整 ADaM 依赖知识图谱。

建议的下一步

  1. 先冻结/回滚当前失败 UI 思路，不再沿着 JSON dashboard 方向修补。
  2. 重新画 UI 工作流：输入准备、文件识别、目标数据集选择、依赖检查、LLM/R 运行、输出审查、reference 比较、audit。
  3. 把 old Shiny UI 当作交互参考，而不是照搬技术栈。
  4. 修正 demo loader：严格按 demo-data 中真实文件角色放置到 study 目录。
  5. UI 首页只讲用户任务，不展示后端 JSON；高级审计页再显示 raw artifacts。
  6. 在产品语言里明确区分：真实执行、stub、mock、结构验证、临床验证。
