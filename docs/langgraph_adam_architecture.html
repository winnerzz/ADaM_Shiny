ADaM Agent 的 LangGraph 产品架构

这份文档解释一个新的多智能体架构应该如何建立。重点不是追求“多个 Agent 聊天”，而是把 SDTM 到 ADaM 的过程做成可暂停、可审查、可恢复、可追溯的工程工作流。

1. 先讲本质：为什么不能继续用一个大提示词

现有 Shiny 原型的核心是：把 Spec、SDTM 摘要、规则说明拼成一个大 prompt，让模型一次性生成 R 代码。这个方式可以做演示，但很难做成稳定产品。

大提示词的问题

  • 模型既要理解资料，又要设计派生逻辑，还要写代码。
  • 一旦错了，很难判断是 Spec 错、lineage 错、代码错，还是数据本身有问题。
  • 所有中间判断都藏在模型输出里，不容易审计。
  • 多数据集并行、回退、修复都会变成一堆复杂 if/else。

LangGraph 的思路

  • 把流程拆成多个明确步骤。
  • 每一步读入结构化状态，产出结构化结果。
  • 失败时可以路由到代码修复、Spec 修订、lineage 修订或人工处理。
  • 每一步都能保存快照，方便恢复和审计。
简单说：新的系统不应该是“一个聪明模型一次性完成所有事”，而应该是“一个可控流程，必要时调用模型，关键点有人审查”。

2. 总体架构：两层图，而不是一条直线

真实研究不是只生成一个数据集。通常有 ADSL、ADAE、ADCM、ADLB、ADVS、ADTTE 等多个目标数据集。它们之间还有依赖关系，例如 ADAE 常常依赖 ADSL 中的治疗日期和治疗组。

因此新系统要分成两层：

StudyGraph：研究级主图

负责整个研究的总体编排。

  • 读取研究输入。
  • 识别目标 ADaM 数据集。
  • 建立数据集依赖关系。
  • 决定哪些数据集可以并行。
  • 汇总所有数据集结果。
  • 生成最终审计包。

DatasetGraph：数据集子图

每个 ADaM 数据集一个独立子流程。

  • 为当前数据集生成 lineage。
  • 草拟或读取 Spec。
  • 生成该数据集的 R 代码。
  • 运行、校验、比较、修复。
  • 独立记录修复次数和人工决策。
StudyGraph
  scan_study_inputs
  build_dataset_dependency_graph
  dispatch_ready_datasets
    -> DatasetGraph(ADSL)
    -> DatasetGraph(ADAE)
    -> DatasetGraph(ADCM)
  reduce_dataset_results
  package_study_audit
关键点：不要用一个全局 repair_attempts。ADAE 的修复次数不应该影响 ADCM。每个 DatasetGraph 必须有自己的状态。

3. 数据集依赖：为什么需要先生成 ADSL

多数据集不是简单并行。某些数据集必须依赖另一个数据集。最常见的是 ADSL，它提供受试者级信息，比如治疗组、首次给药日期、末次给药日期。

Study 输入SDTM、define、Spec、参考 ADaM
→
建立依赖图谁必须先生成
→
ADSL 子图先完成 subject-level
ADAE 子图可依赖 ADSL
ADCM 子图可依赖 ADSL
ADLB 子图可依赖 ADSL
ADVS 子图可依赖 ADSL

工程上可以把这种关系保存为一个依赖表： 

{
  "ADSL": [],
  "ADAE": ["ADSL"],
  "ADCM": ["ADSL"],
  "ADLB": ["ADSL"],
  "ADVS": ["ADSL"]
}

主图先跑没有依赖的数据集。等 ADSL 完成后，再分发 ADAE、ADCM、ADLB、ADVS 等子图并行执行。

4. DatasetGraph：一个数据集内部怎么流转

每个数据集都走类似流程，但状态彼此隔离。 

DatasetGraph(dataset = "ADAE")

profile_dataset_inputs
  -> draft_lineage
  -> route_lineage_risk
     -> silent_pass or human_review_lineage
  -> draft_spec
  -> route_spec_risk
     -> silent_pass or human_review_spec
  -> generate_code
  -> static_check
  -> run_sandbox
  -> validate_output
  -> compare_reference
  -> diagnose_failure
     -> repair_code
     -> revise_spec
     -> revise_lineage
     -> human_escalation
  -> finalize_dataset
节点 用普通话解释 主要产物
profile_dataset_inputs 看这个数据集可能需要哪些 SDTM 域和变量。 输入画像、列清单、缺失率、候选键。
draft_lineage 画出源变量到目标变量的血缘关系。 lineage graph、风险点、待确认问题。
draft_spec 生成或整理机器可读的 ADaM Spec。 变量名、标签、类型、来源、派生规则。
generate_code 根据已确认的 lineage/spec 生成 R 代码。 R derivation script。
static_check 执行前检查代码有没有明显风险。 静态检查报告。
run_sandbox 在隔离环境运行 R 代码。 生成的 ADaM 数据。
validate_output 检查输出变量、类型、主键、缺失等。 校验报告。
diagnose_failure 判断失败根因在哪里。 下一步路由：修代码、修 Spec、修 lineage 或找人。

5. 失败不能只修代码：要能回退到 Spec 和 Lineage

旧思路通常是：代码跑错了，就让模型修代码。但实际工作里，报错不一定是代码问题。

代码错误

例如变量名写错、join 顺序错、日期解析函数用错。

走 repair_code

Spec 错误

例如 Spec 漏了前置变量，或者派生规则互相冲突。

回到 revise_spec

Lineage 错误

例如把来源域猜错了，导致后续代码无论怎么修都不对。

回到 revise_lineage 
diagnose_failure
  if root_cause == "code_error":
      repair_code -> static_check
  if root_cause == "spec_error":
      revise_spec -> maybe_human_review_spec -> generate_code
  if root_cause == "lineage_error":
      revise_lineage -> maybe_human_review_lineage -> draft_spec
  if root_cause == "data_issue":
      human_escalation
  if no_progress_after_retry:
      stop_with_audit
这是产品级架构的关键。否则系统会在错误 Spec 上反复修代码，形成死循环。

6. CDISC 文档怎么用：不是一次性检索，而是随时可查工具

CDISC 文档、Pinnacle 21 规则、公司标准不能在流程开头一次性摘要完就结束。模型在代码生成或修复时，可能临时需要查某条规则。

因此 Reference Layer 应该做成工具，而不是单独的串行节点。

文档放在哪里

references/
  CDISC/
    ADaM_IG/
    SDTM_IG/
    Controlled_Terminology/
    Define_XML/
    TAUG/
    P21_Rules/
  company_standards/
  reference_manifest.yaml

工具长什么样

search_cdisc_reference(query, dataset_role, variable)
search_p21_rule(rule_id)
search_company_standard(topic)
read_define_metadata(dataset, variable)
find_controlled_term(codelist, value)

这些工具可以绑定给多个 LLM 节点：

  • draft_lineage：不确定变量来源时查文档。
  • draft_spec：不确定变量类型或派生规则时查文档。
  • generate_code：不确定实现方式时查公司标准或既有模板。
  • diagnose_failure：遇到 P21 规则或比较差异时查规则。
  • repair_code：修复前先查对应标准，不靠模型记忆硬猜。
重点：CDISC 文档不是被全部塞进 prompt，而是作为可查询的产品资产存在。

7. 人工审查：不是每步都点 Approve

人工审查是必须的，但不能滥用。否则 20 个数据集、每个数据集 3 次审批，很快就变成几十上百次点击。

正确方式是风险驱动。 

如果 confidence >= 0.90
且没有规则冲突
且是常规直接映射
    -> silent_pass

如果 confidence < 0.90
或有多个可能来源
或有规则冲突
或会影响关键变量
    -> human_review
情况 处理方式
DM.USUBJID 直接映射到 ADSL.USUBJID 通常静默通过，写入审计记录。
TRTEMFL 规则有多种解释 要求人工审查。
Spec 里 Source 为空，但变量是关键日期 要求人工审查。
P21 规则冲突 要求人工审查或规则解释。
人工审查应该是“批量审高风险项”，而不是“每个变量点一次确认”。

8. State 和文件：小对象放状态，大文件放路径

之前的极端做法是 State 里只放路径。这会导致每个节点反复读写小 JSON，增加 I/O。更合理的是混合模式。

适合放进 State

  • 当前数据集名。
  • draft_spec 的 JSON 字典。
  • lineage graph 的 JSON。
  • generated_code 字符串。
  • static_report 摘要。
  • validation_report 摘要。
  • confidence、risk、routing decision。
  • human decision 记录。

适合只放路径和 hash

  • 原始 SDTM 大表。
  • 参考 ADaM 数据集。
  • 生成的 XPT/CSV/SAS7BDAT。
  • 大型 compare 明细表。
  • CDISC 原始 PDF。
  • 最终 HTML/PDF 审计报告。

这样既能让 LangGraph checkpointer 保存关键过程，又不会把大矩阵塞进状态系统。

11. 第一阶段应该做什么

第一阶段不要急着做完整 ADaM 生成。先证明这个架构能运行、能保存状态、能暂停恢复。

  1. 建立目录骨架。
  2. 定义 StudyState 和 DatasetState。
  3. 实现一个最小 StudyGraph。
  4. 实现一个最小 DatasetGraph。
  5. 让 ADSL 和 ADAE 两个子图能被主图调度。
  6. 加入一个风险驱动的人工暂停点。
  7. 把每一步状态写入 checkpoint。
  8. 生成一个简单 audit manifest。
第一阶段最小流程：

scan_study_inputs
  -> build_dataset_dependency_graph
  -> dispatch_dataset_graphs
  -> dataset_stub
  -> reduce_dataset_results
  -> package_audit_stub
第一阶段成功标准不是“生成正确 ADaM”，而是“架构能正确调度、暂停、恢复、记录和汇总”。

12. 这套架构的底线原则

  • LLM 不是唯一大脑，确定性工具优先。
  • 每个数据集有独立状态，不能共享修复次数。
  • 失败后必须先诊断根因，不能只修代码。
  • CDISC 文档是可查询工具，不是一次性 prompt 内容。
  • 人工审查由风险触发，不做无意义审批。
  • 小结构放 State，大文件放 Artifact Store。
  • 每一步都要可追溯、可恢复、可审计。

如果遵守这些原则，这个系统才会从“提示词工程原型”变成真正的 agent 产品架构。
